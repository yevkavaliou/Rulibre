# Конфигурация и пути — этап №4

Дата: 11 октября 2026 года.

`Config.library_path` теперь имеет тип `PathBuf`. `sanitize_path(&str)` возвращает
`Result<PathBuf, Error>`. Ядро не преобразует пути через `to_string_lossy`.

## Правила путей и совместимость

- В пользовательском вводе удаляются внешние пробелы, одна пара одинаковых
  кавычек (`'` или `"`), затем пробелы внутри этой пары по краям. Внутренние
  пробелы и Unicode сохраняются. Одиночная кавычка остаётся частью пути.
- Пустой результат возвращает `InvalidInput`, без обращения к текущему каталогу.
- `~`, `~/…` и `~\…` раскрываются через домашний каталог. Если он недоступен,
  возвращается `Unavailable`. `~user` и переменные окружения не раскрываются.
- Относительные пути становятся абсолютными от текущего рабочего каталога
  процесса, включая пути из старого TOML. Наличие каталога не требуется для
  разрешения пути; ссылки не раскрываются через canonicalize.
- При сохранении записывается абсолютный путь. При загрузке/сохранении нативного
  `PathBuf` пробелы и кавычки не удаляются: это уже данные, а не пользовательский
  ввод. TOML сохраняет прежний ключ `library_path` и строковое значение.
- Пустое `library_path = ""` остаётся допустимым шаблоном для `--config`, но
  никогда не считается библиотекой. Функция загрузки не проверяет наличие
  библиотеки: TUI и Tauri проверяют каталог и файл `metadata.db` перед сканированием.
  Это проверка структуры каталога, а не целостности SQLite.
- Отсутствующий конфиг — `Ok(None)`, некорректный TOML — `InvalidData`, ошибка
  чтения — `Io`. Пути, которые невозможно сериализовать без потери Unicode,
  возвращают ошибку; TOML и строковый IPC не поддерживают такие пути.

## Сохранение

Сериализация происходит до файловых изменений. В каталоге назначения создаётся
уникальный временный файл через `create_new`; выполняются `write_all`, `sync_all`,
закрытие файла и `fs::rename` с заменой назначения. Старый конфиг предварительно
не удаляется. Временный файл находится на той же файловой системе.
Поведение замены на Windows описано в [документации Rust](https://doc.rust-lang.org/std/fs/fn.rename.html).
Ошибка записи или замены возвращается с операцией и путём конечного конфига.
Удаление временного файла выполняется при выходе из функции, включая ошибки.

Гарантия касается обработанных ошибок записи и замены на доступной файловой
системе. Полная устойчивость к отключению питания не заявляется: каталог после
rename не синхронизируется. При аварийном завершении процесса или отказе удаления
может остаться временный файл. Замена меняет файловый объект; прежние ACL и
метаданные файла специально не переносятся. Одновременные успешные сохранения
имеют политику последней завершившейся замены.

## Проверки

- Windows: `cargo test --locked` — 20 тестов прошли, включая 5 новых.
- `cargo check --locked` — ядро, TUI, scan_metadata прошли.
- `cargo fmt -p rulibre-core -p rulibre -- --check` — прошёл.
- Tauri host: `cargo check --locked -p rulibre-gui` прошёл с временными
  тестовыми `icons/icon.ico` и `dist/index.html`; файлы удалены после проверки.
  Это проверка сборки host, не работающего IPC или frontend.
- WASM не проверен: установлен только `x86_64-pc-windows-msvc`.
- Проверены пустой ввод, одиночные/парные кавычки, пробелы, Unicode, относительные
  пути, домашний каталог, старый TOML, повторное сохранение и удаление metadata.db.
  Тесты №3 продолжают проверять отсутствующий конфиг, плохой TOML и ошибки чтения.
- Подменённая частичная запись возвращает `WriteZero`; старое содержимое и
  отсутствие временных файлов проверены. Реальная Windows-блокировка разрешает
  чтение и запрещает удаление/замену: отказ rename сохраняет старый конфиг,
  временный файл удаляется, после снятия блокировки сохранение проходит.
- Тест отказа сериализации пути с невалидным UTF-8 добавлен для Unix,
  на Windows не выполнялся. Linux/macOS и физические ридеры не проверялись.

Sandbox блокировал rustfmt и rename даже при первом сохранении; успешные проверки
выполнены вне sandbox после разрешения автоматической проверки доступа.
Коммит/PR не создан.

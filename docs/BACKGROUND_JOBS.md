# Фоновые задания ядра

Пункт №13 PRE_UI_PLAN.md, 12 октября 2026 года.

## API и исполнение

`rulibre_core::jobs::JobExecutor::new(parallelism, capacity)` создаёт фиксированный
пул именованных worker-потоков. Оба ограничения должны быть положительными.
Например, `new(2, 16)` допускает два выполняющихся задания и всего 16 незавершённых
заданий, включая очередь. Значения задаёт приложение; скрытого дополнительного
параллелизма внутри этого слоя нет. Новые зависимости не добавлены.

`submit(JobRequest)` принимает операции:

- `Scan { library }` — сканирование с предупреждениями отдельных книг;
- `Metadata { book }` — чтение метаданных с проверкой отмены до/после чтения;
- `Backends` — проверка доступности конвертеров с передачей отмены;
- `ConvertFiles { library, output_dir, files, target }` — планирование по всем
  исходным файлам книги и конвертация внутри worker (добавлено в №14);
- `Convert { library, output_dir, source, target }` — конвертация в существующий
  каталог вне библиотеки, с проверками и политикой публикации этапа №8;
- `Send { book, author, device, options }` — проверка выбранного устройства,
  подготовка по правилам №11 и безопасная передача по правилам №12.

Сканирование, поиск и запуск конвертеров, подготовка и копирование выполняются
в worker-потоках. При отправке запрос содержит снимок выбранного устройства:
смена выбора интерфейса не перенаправляет уже принятое задание. Перед записью
устройство перепроверяется прежним API передачи.

`submit` не ожидает свободного worker и не ждёт результата операции. Для пишущих
заданий он синхронно разрешает путь назначения через `canonicalize`, чтобы
зарезервировать его вместе с алиасами. Поэтому это не обещание отсутствия любых
файловых обращений или нулевой задержки принятия запроса. При недоступном
назначении возвращается `SubmitError::InvalidDestination`. До начала задания
назначение должно существовать; исчезнувший корень устройства не создаётся.

`JobHandle` содержит `JobId`, отдельный канал `events`, `try_result()` и `cancel()`.
ID монотонны и уникальны в пределах одного executor; приложение должно владеть
одним общим executor в течение сессии. Результат получается один раз через
`try_result` или `wait`. Для цикла UI следует опрашивать `events.try_iter()` и
`try_result()`. `wait()` — блокирующая функция для CLI и тестов.

`JobOutput` сохраняет типизированные `ScanReport`, `ConversionResult` или путь
переданной книги. Ошибки выполнения остаются исходными `Error`, включая путь,
категорию и `PartialTransfer` с причиной невозможной очистки. Канал результата
отделён от сериализуемых событий; файловый результат и ошибки не превращаются
в строки внутри ядра. `JobId`, `JobState`, `Stage` и `JobEvent` поддерживают Serde.

## Очередь, состояния и конфликты

Принятое задание получает `Waiting`, затем `Running` и ровно одно конечное
состояние: `Succeeded`, `Failed` или `Cancelled`. Отменённое в очереди задание
переходит непосредственно из `Waiting` в `Cancelled`. События одного задания
упорядочены; порядок событий разных заданий не определён.

Работники забирают задания FIFO. При нескольких работниках порядок окончания
и появления `Running` у разных заданий может отличаться от порядка принятия.
Переполнение возвращает `SubmitError::Full`, остановленный executor — `Closed`.
Отказ принятия не создаёт задания и событий.

Пишущие задания резервируют назначение уже в очереди, до выполнения. Конвертация
резервирует весь каталог вывода; передача — ID устройства и весь корень его
монтирования. Равные канонические пути, их вложенные каталоги и одинаковые ID
считаются конфликтом. На Windows ASCII-регистр пути нормализуется с сохранением
нативного UTF-16. `SubmitError::Conflict` возвращается сразу; автоматического
повтора или молчаливой перезаписи нет. После завершения или отмены ожидающего
задания резервирование снимается. Независимые назначения могут обрабатываться
параллельно; сканирования не резервируют запись.

Это консервативная политика: две разные книги одному ридеру одновременно не
отправляются. Она действует внутри одного executor, не является межпроцессным
замком и не координирует прямые синхронные вызовы прежних API. Защита конечных
файлов и проверка назначения по-прежнему обеспечиваются №8/№12. Конвертация
не создаёт собственный workspace: его владелец и срок хранения результата
задаются приложением. Внутренняя подготовка для передачи владеет временным
workspace до окончания копирования и затем очищает его.

## Прогресс и отмена

События этапов: `Scanning`, `Converting`, `Preparing`, `Copying`.
Для конвертера и подготовки процент не вычисляется. При копировании
`CopyProgress` передаёт реальные `completed` и `total` из цикла записи.
Промежуточные события ограничены приблизительно десятью в секунду; последняя
записанная порция передаётся обязательно. Полный объём означает завершение
копирования байтов, но ещё не успех `sync_all`, проверки устройства и публикации;
успех определяется только конечным состоянием и результатом.

Каналы событий не блокируют workers при медленном интерфейсе. Они не ограничены
по размеру: потребитель должен регулярно читать события или удалить handle,
если результат ему больше не нужен. Удаление handle само по себе не отменяет
работу; недоступный получатель не мешает освобождению резервирования.

Ожидающее задание удаляется из очереди при `cancel()` сразу. Для выполняющегося
задания используется общий `CancellationToken`: конвертер получает токен через
API №8, подготовка и копирование — через №11/№12. Сканер проверяет отмену перед
обходом, между авторами и книгами и перед выдачей результата; отмена всего обхода
является ошибкой, а не предупреждением отдельной книги.

Отмена кооперативная. Она не прерывает уже выполняющийся системный файловый
вызов или чтение одного OPF. Системный запуск конвертера сохраняет прежние
гарантии остановки и ожидания дочернего процесса. Если запись уже успешно
опубликована, поздний запрос отмены не превращает её в `Cancelled`. Ошибка
очистки частичного файла остаётся `Failed` с `PartialTransfer`.

## Завершение приложения

`shutdown(&mut self)` закрывает приём заданий, отменяет очередь и токены активных
заданий, будит ожидающие workers и выполняет `join` каждого потока. Повторный
вызов безопасен. `Drop` вызывает ту же остановку. Если создание очередного
worker не удалось, уже созданные workers также закрываются через `Drop`.

Остановка ждёт окончания текущего непрерываемого системного вызова: жёсткого
таймаута завершения нет. Для интерфейса, который должен показывать состояние
выхода, ожидание остановки нужно организовать вне обработки UI-событий.
Паника операции перехватывается как `Failed`; worker остаётся работоспособным.
Это не распространяется на `panic=abort` или принудительное завершение процесса.

## Проверки и границы этапа

- `cargo test --locked`: 95 тестов проходят, 3 верхнеуровневых теста игнорируются.
  В этом этапе добавлены 14 тестов: 13 для очереди/исполнения и один для отмены
  сканера. Проверены состояния, FIFO, лимиты, отдельные worker-потоки, конфликты
  путей и ID, отмена очереди и активной операции, Drop/join, повторная остановка,
  восстановление после паники, реальные байты прогресса и очистка после отмены.
- `cargo check --locked`: ядро, TUI и `scan_metadata` собираются.
- `cargo fmt -p rulibre-core -p rulibre -- --check`: проходит.
- `cargo clippy --locked -p rulibre-core -p rulibre --all-targets`: проходит;
  прежние предупреждения `collapsible_if` в metadata и `derivable_impls` в TUI.

Проверки выполнены на Windows вне sandbox; TMP/TEMP тестов направлены в `target`.
Тесты передачи используют обычные временные каталоги, подменяя только системную
проверку тома; цикл записи, прогресс, токен отмены и очистка реальные.
Предыдущий тест конвертера подтверждает остановку/ожидание дочернего процесса
при отмене. Настоящие ридеры, конвертация валидной книги, Linux/macOS runtime,
WASM и GUI/IPC в этом этапе не проверялись.

API добавлено без поломки прежних синхронных вызовов. Подключение TUI/Tauri к
новому executor и доставка заданий через IPC относятся к №14: существующие
клиенты пока сохраняют прежний способ вызова операций. Новый UI не создавался.
Коммит и PR не создавались.

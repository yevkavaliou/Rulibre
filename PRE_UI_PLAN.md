# Подготовка Rulibre к новому графическому интерфейсу

Дата: 11 октября 2026 года.

Репозиторий: https://github.com/yevkavaliou/Rulibre.
Оригинал: https://github.com/Glydric/Rulibre.
Исходная ревизия: `7d926068619909207518ebddc1754e23de95ae05`.

Документ описывает подготовку ядра, конвертации и работы с устройствами. Разработка Iced UI сюда не входит. Адаптация существующих TUI и Tauri допускается только для сохранения работоспособности после изменений общего API.

## Правила выполнения

- Порядок строгий: №1 → №2 → … → №15. Начинать следующий пункт можно только после завершения предыдущего, включая указанные проверки. Это порядок выполнения проекта, даже если отдельные изменения технически независимы.
- Статус каждого пункта — только «сделано» или «не сделано». Частичную работу записывать в примечания, не менять статус на «сделано».
- Тесты добавлять вместе с исправлениями. Финальная проверка дополняет проверки этапов, а не заменяет их.
- Изменение публичного API сопровождается минимальной адаптацией его потребителей в том же этапе: TUI, Tauri и `scan_metadata` должны продолжать собираться на доступных целевых платформах.
- После выполнения заполнять примечания: что изменено, какие проверки проведены, их результат, ссылка на коммит/PR при наличии и оставшиеся ограничения. Не выдавать проверку на временных каталогах за проверку на физическом ридере.
- Найденные проблемы подтверждены просмотром кода. Исходная сборка, внешние конвертеры и реальные ридеры пока не проверялись. Предложенные ниже API и политика хранения результатов — план реализации, а не уже существующие возможности.

## Проблема №3. Сделать ошибки ядра управляемыми

### 1. Проблема

`scanner::scan_library` завершает процесс через `process::exit(1)`. Конфигурация использует `expect`/`unwrap`. Некоторые ошибки чтения скрываются через `.ok()` и `.flatten()`; часть функций возвращает только строки ошибок.

### 2. Почему это проблема и как должно быть на самом деле

Библиотека не должна закрывать приложение при недоступном каталоге или плохом файле. Вызывающий код должен различать отсутствие данных, ошибку доступа, некорректный формат и сбой внешней программы.

### 3. Решение

Ввести общий тип ошибок ядра с контекстом операции и пути. Для ошибочных операций использовать `Result`; для допустимого отсутствия данных — `Result<Option<T>, Error>`. Отделить критическую ошибку сканирования корня от предупреждений по отдельным книгам. Удалить завершение процесса и паники из обработки ожидаемых ошибок ядра. Текст сообщений формировать на границе приложения.

Критерий завершения: отсутствующий/недоступный каталог и повреждённые данные возвращают ошибки или предупреждения; библиотечные вызовы не завершают процесс. Добавлены регрессионные тесты. Потребители API адаптированы.

### 4. Текущий статус

**сделано**

### 5. Примечания после выполнения

Введены Error/ErrorKind с операцией, путём, исходной I/O/parse-ошибкой и данными сбоя процесса. scan_library возвращает Result<ScanReport, Error>: ошибка корня отделена от предупреждений подкаталогов. Config, OPF, поиск исходного файла, конвертация и передача возвращают Result; допустимое отсутствие данных — Ok(None). Удалены process::exit и паники ожидаемых ошибок из библиотечного кода, включая одиночную кавычку в sanitize_path. Адаптированы TUI, scan_metadata, Tauri host и изменённые WASM-вызовы. 15 тестов, check ядра/TUI и форматирование прошли. Tauri host прошёл check с временными тестовыми icon.ico и dist, удалёнными после проверки; исходные ограничения GUI и отсутствие WASM target сохраняются. ## Проблема №4. Исправить конфигурацию и обработку путей

### 1. Проблема

`Config::load` не различает отсутствующий конфиг, некорректный TOML и ошибку чтения. Сохранение может вызвать панику. `sanitize_path` срезает строку без проверки длины: ввод из одной кавычки способен вызвать панику.

### 2. Почему это проблема и как должно быть на самом деле

Первый запуск должен отличаться от повреждённой конфигурации. Любой пользовательский ввод должен обрабатываться без паник; неудачная запись не должна портить прежний конфиг.

### 3. Решение

Обрабатывать парные кавычки только при достаточной длине строки. Определить правила пустого ввода, относительных путей и `~`; сохранять пути как `PathBuf` внутри ядра без ненужного преобразования через `to_string_lossy`. Проверять библиотеку при использовании сохранённого пути. Сохранять конфигурацию через временный файл и безопасную замену с учётом поведения Windows; возвращать ошибки чтения и записи.

Критерий завершения: покрыты пустой ввод, одиночные кавычки, пробелы, Unicode, некорректный TOML, отсутствующий конфиг и сбой сохранения. Старый конфиг не теряется при неуспешной записи.

### 4. Текущий статус

**сделано**

### 5. Примечания после выполнения

Config.library_path переведён на PathBuf; sanitize_path возвращает Result и обрабатывает пустой ввод, кавычки, пробелы, Unicode, относительные пути и домашний каталог. Сохранение выполняется через уникальный временный файл, sync_all и замену без предварительного удаления старого конфига. TUI/Tauri адаптированы; сохранённая библиотека проверяется перед использованием. Прежняя TOML-схема совместима. 20 тестов, check ядра/TUI/scan_metadata и форматирование прошли; частичная запись и реальная Windows-блокировка подтвердили сохранность старого файла и очистку временного. Tauri host check прошёл с временными тестовыми icon.ico/dist, удалёнными после проверки. WASM target отсутствует; Linux/macOS и физические ридеры не проверены. Правила, гарантии и ограничения: [docs/CONFIG_PATHS.md](docs/CONFIG_PATHS.md). Коммит/PR не создан.

## Проблема №5. Исправить модель форматов и сканирование

### 1. Проблема

`extract_format` считает форматом почти любое расширение. `Book.formats` хранит строку вида `EPUB, PDF`, а исходный файл выбирается повторным обходом каталога. Нет устойчивого идентификатора книги в модели.

### 2. Почему это проблема и как должно быть на самом деле

Служебные файлы могут попасть в конвертер. Строковый список смешивает данные и представление. Выбор книги и файла должен быть однозначным и не зависеть от порядка `read_dir`.

### 3. Решение

Ввести тип формата и список файлов книги с точными путями. Разделить распознаваемые форматы, допустимые входы конвертеров и поддерживаемые устройствами форматы. Исключить OPF, изображения обложек, временные и неизвестные файлы; корректно отличать `.epub` от `.kepub.epub` независимо от регистра. Ввести идентификатор книги, используя Calibre ID из имени каталога при наличии и определённый fallback. Оставить строки форматов только в адаптерах отображения.

Критерий завершения: тесты на служебные файлы, неизвестные расширения, смешанный регистр, двойное расширение, несколько файлов одного формата и стабильный порядок. Ошибки отдельных каталогов видны в отчёте сканирования.

## Проблема №6. Сделать чтение метаданных предсказуемым

### 1. Проблема

`parse_opf` возвращает одинаковый `None` при отсутствии OPF, ошибке доступа и некорректном XML. Простой `strip_html` удаляет теги без сохранения границ абзацев и декодирует только несколько HTML-сущностей.

### 2. Почему это проблема и как должно быть на самом деле

Приложение должно показывать книгу даже без OPF, но сообщать о повреждённых данных. Описание должно оставаться читаемым, а метаданные — иметь определённый приоритет перед именами каталогов.

### 3. Решение

Различать отсутствие файла и ошибку парсинга. Определить fallback для названия и автора из сканера. Нормализовать описание с сохранением абзацев и корректным декодированием сущностей. Сохранить диагностику неизвестных тегов. Не превращать парсер в редактор OPF или базы Calibre.

Критерий завершения: тесты для отсутствующего/повреждённого OPF, namespace, нескольких авторов, серии, идентификаторов и HTML-описаний. Ошибка метаданных одной книги не срывает работу с библиотекой.

### 4. Текущий статус

**сделано**

### 5. Примечания после выполнения

Сохранён контракт parse_opf: отсутствие OPF — Ok(None), ошибки чтения/XML/структуры — Err с путём. Добавлены read_metadata и независимый fallback названия/автора из каталогов; непустые OPF-поля имеют приоритет. Сканер использует OPF-имена, сохраняет книгу с fallback при ошибке и добавляет предупреждение; ID и файлы не меняются. HTML/CDATA/XHTML описания разбираются HTML-парсером с декодированием сущностей, границами абзацев/переносов и исключением невидимого содержимого. Сохранена и расширена диагностика неизвестных тегов/meta; адаптированы TUI и Tauri/панель GUI. 34 теста ядра (6 новых), check ядра/TUI/scan_metadata и форматирование прошли. ## Проблема №7. Защитить библиотеку Calibre от несогласованных изменений

### 1. Проблема

Конвертер пишет новые файлы прямо в каталог книги, но не регистрирует новый формат в `metadata.db`. Сканер Rulibre и Calibre могут показывать разные наборы форматов.

### 2. Почему это проблема и как должно быть на самом деле

Нельзя считать создание файла полноценным добавлением формата в Calibre. Подготовка книги для устройства не должна незаметно изменять исходную библиотеку.

### 3. Решение

Для этого этапа принять режим библиотеки только для чтения: временные результаты конвертации хранить в отдельном рабочем каталоге/кэше, экспорт — в явно выбранном каталоге вне библиотеки. Передавать каталог результата в API конвертации отдельно от исходного файла. Определить очистку временных результатов и проверять, что выход не совпадает с источником и не попадает в библиотеку.

Запись через `calibredb` и полноценное управление базой Calibre оставить за пределами этого плана. Это предлагаемая политика MVP, которую нужно зафиксировать перед реализацией конвертера.

Критерий завершения: сценарии подготовки/конвертации не меняют файлы исходной библиотеки и `metadata.db`; политика хранения документирована и проверена тестами.

### 4. Текущий статус

**сделано**

### 5. Примечания после выполнения

Принят режим библиотеки только для чтения. API конвертации принимает корень библиотеки, отдельный выходной каталог и источник; возвращает точный ожидаемый путь. Запрещены вывод внутрь библиотеки (включая другую Calibre-библиотеку и ссылки/junction), совпадение с источником и существующее конечное имя. Временные результаты находятся в уникальном workspace под системным TEMP; подготовка для устройства очищает его после копирования/ошибки, TUI/Tauri — при завершении приложения. Постоянный экспорт через API требует явно выбранного каталога вне библиотеки. Клиенты не добавляют результат в список форматов исходной книги. 41 автоматический тест ядра прошёл (7 новых), check ядра/TUI/scan_metadata и форматирование прошли. Tauri host check и тест совместимости транспортной модели прошли с временными icon.ico/dist, удалёнными после проверки. Отдельный opt-in тест настоящего ebook-convert 8.16.2 (TXT → EPUB) прошёл с проверкой неизменности библиотеки и очистки. Проверки выполнялись вне Windows sandbox из-за отказа canonicalize/rustfmt, с TMP/TEMP в workspace. kepubify отсутствует; WASM target, Linux/macOS, реальные ридеры и запуск GUI/IPC не проверены. Политика хранения, очистка после аварийного завершения и границы гарантий: [docs/LIBRARY_READ_ONLY.md](docs/LIBRARY_READ_ONLY.md). Коммит/PR не создан.

## Проблема №8. Исправить выбор и выполнение конвертации

### 1. Проблема

Fallback может выбрать служебный файл. Доступность конвертеров сводится к двум `bool`. Успешный код завершения считается достаточным подтверждением результата. Обработка KEPUB различается между путями конвертации.

### 2. Почему это проблема и как должно быть на самом деле

Преобразование должно использовать допустимый источник, подходящий backend и возвращать точный путь существующего результата. Отсутствие инструмента должно отличаться от его неисправности.

### 3. Решение

Использовать модель файлов из №5 и выходной каталог из №7. Определить детерминированный приоритет источников и маршруты конвертации по реальным возможностям инструментов; отдельно проверить поддержку KEPUB конкретным backend. ## Проблема №9. Исправить обнаружение устройств

### 1. Проблема

На Windows существующий диск из диапазона `D:`–`Z:` считается Kobo без проверки. На Linux/macOS поиск ограничен заранее заданными именами каталогов. Возвращается только одно устройство.

Отделить перечисление смонтированных томов от определения типа ридера. Для Windows использовать сведения о томах; для Linux/macOS — реальные точки монтирования. Правила подтвердить документацией или содержимым реальных устройств при реализации; неоднозначный том не классифицировать автоматически.

Ограничить поддержку смонтированными файловыми системами: MTP требует отдельной реализации и не должен выглядеть как поддержанный сценарий.

## Проблема №12. Сделать передачу книги безопасной при сбоях

### 1. Проблема

`fs::copy` пишет прямо в конечный файл и может перезаписать существующий. Автор используется как компонент пути без специальной проверки. При исчезновении mount point создание каталога может привести к записи на локальную файловую систему вместо устройства.

### 2. Почему это проблема и как должно быть на самом деле

Обрыв копирования не должен оставлять готовый с виду повреждённый файл или уничтожать прежнюю книгу. Путь назначения должен оставаться внутри выбранного устройства, а подключение — перепроверяться перед записью.

Нормализовать компоненты имён, исключить абсолютные пути, `..` и выход через ссылки за пределы назначения. Не создавать заново исчезнувший корень монтирования. Копировать во временный файл в каталоге назначения, проверять завершение и только затем публиковать конечное имя. По умолчанию возвращать конфликт имени, без молчаливой перезаписи. Учитывать особенности файловой системы устройства и поддержать очистку частичного файла, когда устройство доступно.

Критерий завершения: тесты на конфликт, опасное имя, отсутствие прав, ошибку записи, отключение и отмену. Прежний конечный файл сохраняется при сбое. Проверка физического устройства записана отдельно; невозможность очистки после отключения отражена в результате.

## Проблема №14. Проверить интеграцию нового API с существующими клиентами

### 1. Проблема

### 3. Решение

Унифицировать транспортные модели либо добавить проверки совместимости, не подтягивая файловую логику в WASM. ## Проблема №15. Подтвердить готовность ядра и закрепить проверки

### 1. Проблема

Без общей проверки исправленные модули могут расходиться по контрактам. Локальные успехи не подтверждают работу обнаружения и копирования на других ОС и реальных устройствах.

### 2. Почему это проблема и как должно быть на самом деле

До начала нового интерфейса нужна проверенная цепочка: конфигурация → сканирование → метаданные → обнаружение → подготовка → передача. Ограничения должны быть явно записаны.

### 3. Решение

Выполнить итоговые тесты ядра/TUI, форматирование и Clippy; проверить доступные сборки существующего GUI. Настроить CI для Windows, Linux и macOS с тестами платформенной логики и фикстурами томов. Провести интеграционный сценарий на копии тестовой библиотеки с проверкой неизменности исходных файлов, отсутствующим конвертером, конфликтом назначения, отменой и отключением.

Провести отдельный smoke-test с доступными настоящими Kobo/Kindle и конвертерами. Если оборудования нет, зафиксировать это как непроверенное ограничение; не помечать соответствующую проверку успешной. Обновить README и документацию API: форматы, устройства, внешние зависимости, режим библиотеки только для чтения, ручной выбор, ошибки и задания. Финально заполнить примечания всех этапов.

Критерий завершения: обязательные автоматические проверки проходят; ограничения и результаты физической проверки записаны; нет известных критических ошибок, способных завершить приложение при ожидаемом сбое, принять обычный диск за ридер или незаметно перезаписать данные. При отсутствии физической проверки готовность означает готовность к разработке UI, а не подтверждённую поддержку всех устройств.
